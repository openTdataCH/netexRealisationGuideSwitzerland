Overview

Demand responsive traffic (DRT, German: On-Demand-Verkehr, ODV) covers services that only run, or only serve some stops, when passengers have booked or requested them.

The Swiss DRT types and their LineType are defined in the sheet LineType of the mapping table for NeTEx 2.0:

Table: Swiss DRT types

Remarks from the mapping table LineType TransportSubmode Swiss DRT type
Fixed stops, operated on request. flexible BusSubmode demandAndResponseBus 1 – Bedarfslinie
Combines fixed and flexible elements; passengers book individual trips, shared vehicle routing. mixedFlexibleAndFixed BusSubmode demandAndResponseBus 2 – Anrufsammelverkehr
Flexible routing along a geographic corridor; stops constrained to the corridor. corridorService BusSubmode demandAndResponseBus 3 – Richtungsband, örtlich disponierter Bus
Area-wide service with time-based operating windows; time restriction via AvailabilityCondition / Timeband. freeAreaAreaWide BusSubmode demandAndResponseBus 4 – Zeitbezogener Flächenverkehr
Fully area-wide, no fixed stops. freeAreaAreaWide BusSubmode demandAndResponseBus 5 – Freier Flächenverkehr

Modelling Principles

A DRT offer is delivered with the same frames and elements as any other timetable. The flexibility is expressed in these places:

  • Line: every DRT service is a Line in the ServiceFrame with the LineType of its Swiss DRT type and BusSubmode demandAndResponseBus, see Line and LineType.
  • Line/bookingArrangements: holds the booking conditions and the rules of the service, see Booking and Rules on the Line.
  • ServiceJourney: a single on-demand journey has FlexibleServiceProperties referencing the BookingArrangement of the Line (example 04), see FlexibleServiceProperties.
  • StopPointInJourneyPattern: a request stop has RequestStop true and a request method; a flexible stop references the BookingArrangement, see Request Stops.
  • ServiceFacilitySet and Notice: reservation offers from HRDF are delivered as facility and Notice, see Reservation as Service Facility.
  • TypeOfPlace: stops are typed as drtCollectionPoint or regularStop, see Collection Points.
  • FlexibleStopPlace and FlexibleStopAssignment: the service area of the types 3 to 5, see Service Areas.

Line replaces FlexibleLine (forbidden in the ServiceFrame template), and LineType replaces TypeOfFlexibleService (mapping table, sheet LineType).

Line and LineType

→ Glossary definition

Purpose

General rules for Line are in Service Frame. LineType is expected (Line template); its values are defined in the mapping table.

Usage Notes

  • A DRT line gets the LineType of its Swiss DRT type (see Overview) and BusSubmode demandAndResponseBus.
  • fixed is the default for all non-DRT lines. If LineType is omitted, fixed is assumed.
  • The values mainRouteWithFlexibleEnds, flexibleAreasOnly, hailAndRideSections, fixedStopAreaWide and mixedFlexible are not used in the Swiss profile.

Example

<Line id="ch:1:slnid:1026470" version="1" responsibilitySetRef="ch:1:ResponsibilitySet:BLT">
  <!-- ... -->
  <TransportMode>bus</TransportMode>
  <TransportSubmode>
    <BusSubmode>demandAndResponseBus</BusSubmode>
  </TransportSubmode>
  <!-- ... -->
  <LineType>flexible</LineType>
  <TypeOfProductCategoryRef ref="ch:1:TypeOfProductCategory:B" version="1"/>
  <bookingArrangements>
    <BookingArrangement id="ch:blt:generated:BOOK:29013" version="1">
      <BookingMethods>mobileApp</BookingMethods>
      <BookWhen>advanceOnly</BookWhen>
      <BookingNote>Einstieg nur auf Voranmeldung mind. 30 Min. vor der Fahrt.</BookingNote>
    </BookingArrangement>
  </bookingArrangements>
</Line>

Booking and Rules on the Line

Purpose

Line/bookingArrangements holds four kinds of elements:

Table: Elements in Line/bookingArrangements

Element Describes
BookingArrangement How to book.
ServiceBookingArrangement How to book, with additional elements for booking duration and charges.
ServiceCompetitiveCondition What the service may do and may not do in relation to classical public transport.
ServiceEligibilityCondition Who can use the service.

Usage Notes

  • Several ServiceEligibilityConditions are combined with OR (e.g. “senior or child”). This may require splitting a service.
  • Line/bookingArrangements is of type serviceBookingArrangements_RelStructure and can hold all four elements. bookingArrangements in ServiceJourney, FlexibleServiceProperties and StopPointInJourneyPattern stays bookingArrangements_RelStructure: only BookingArrangement or BookingArrangementRef. ServiceBookingArrangement, ServiceCompetitiveCondition and ServiceEligibilityCondition are therefore only possible in Line/bookingArrangements.
  • The bookingArrangements of the Line are valid for the whole Line; a lower level supersedes a higher level (XSD documentation of Line/bookingArrangements).

BookingArrangement

Purpose

Describes how, when and where a DRT service is booked.

Table: Elements of BookingArrangement

Element Values / type
BookingContact Contact details of the booking office.
BookingMethods callDriver, callOffice, online, phoneAtStop, text, mobileApp, atOffice, none, other (list)
BookingAccess public, authorisedPublic, staff, other
BookWhen / BuyWhen advanceOnly, untilPreviousDay, dayOfTravelOnly, advanceAndDayOfTravel, timeOfTravelOnly, subscriptionChargeMoment, other
LatestBookingTime Time
MinimumBookingPeriod / MaximumBookingPeriod Duration
BookingUrl URI
bookingUrls BookingUrl (URI), BookingDeepUrl (Endpoint, parameterDescriptions) or BookingService (Endpoint, EndpointVersion, BookingServiceType, SupportedSteps); at least one entry.
BookingNote Text

BookingServiceType: tomp, osdm, bob, trias, ojp, other. SupportedSteps (list): tripPlanning, pricing, availability, booking, reservation, fulfillment, full, other.

Usage Notes

  • From the HRDF conversion only a BookingNote can be passed at the moment. With native NeTEx handling more information can be transferred (ServiceJourneyPattern template).
  • In a ServiceJourneyPattern, the BookingArrangement is referenced with BookingArrangementRef; an inline BookingArrangement is ignored.
  • BookingArrangement is still needed even though ServiceBookingArrangement contains all its elements: ServiceJourney, FlexibleServiceProperties and StopPointInJourneyPattern can only hold a BookingArrangement or a BookingArrangementRef (see Booking and Rules on the Line).

ServiceBookingArrangement

Purpose

Contains the elements of BookingArrangement and additionally MinimumBookingDuration, MaximumBookingDuration, DepositRequired and BookingChargeType (fullAmount, blockFullAmountOnCard, deposit, none, other).

ServiceCompetitiveCondition

Purpose

Describes restrictions of the DRT service towards classical public transport. Besides Name and Description it contains exactly one of three groups (choice in the XSD).

Table: Elements of ServiceCompetitiveCondition

Group Element Meaning
Distance transferRestrictions / routingConstraintZones Restrictions towards other services. If not set, the rules apply in general.
Distance MinimalDistanceFromClassical Distance in metres to the line/service or classical public transport in general: the minimum walking distance from the next StopPlace of classical public transport.
Distance TemporalDistanceFromClassicalBefore / TemporalDistanceFromClassicalAfter Temporal distance to the service/transfer in the routing constraint or classical public transport in general, before / after the departure at a reasonably nearby stop.
Dominance PenaltyTravelTimeFactor / PenaltyTransferTimeFactor / WalkTimeFactor Factors for the comparison with classical public transport (default 1.0).
Dominance PenaltyTravelTimeOffset Offset in the calculation of the dominance (default PT0S).
Dominance MinimumTravelDuration / MaximumTravelDuration Minimum (default PT0S) and maximum travel duration allowed for the service.
Interchange InterchangeBetweenFlexibleServicesAllowed Default false.
Interchange InterchangeWithConventionalServicesAllowed Default false.

Example

<ServiceCompetitiveCondition id="ch:1:ServiceCompetitiveCondition:1" version="1">
  <MinimalDistanceFromClassical>200</MinimalDistanceFromClassical>
  <TemporalDistanceFromClassicalBefore>PT15M</TemporalDistanceFromClassicalBefore>
</ServiceCompetitiveCondition>

ServiceEligibilityCondition

Purpose

Describes who can use the service. Each condition contains exactly one of UserProfile, CommercialProfile, ResidentialQualification or CompanionProfile.

Example

<ServiceEligibilityCondition id="ch:1:ServiceEligibilityCondition:1" version="1">
  <UserProfile id="ch:1:UserProfile:1" version="1">
    <MinimumAge>65</MinimumAge>
  </UserProfile>
</ServiceEligibilityCondition>

Request Stops

Purpose

Request stops are set in the StopPointInJourneyPattern (see Service Frame). The mapping from HRDF is defined in the sheet Haltecode of the mapping table:

Table: Request stops (Bedarfshalt, HRDF *A X)

HRDF ForAlighting ForBoarding RequestStop Request method
Bedarfshalt true true true BoardingRequestMethod and AlightingRequestMethod
Bedarfshalt nur zum Einsteigen false true true BoardingRequestMethod
Bedarfshalt nur zum Aussteigen true false true AlightingRequestMethod

Usage Notes

  • StopUse is access, at stations with BHFArt 3 interchangeOnly.
  • A flexible stop references the BookingArrangement with BookingArrangementRef (ServiceJourneyPattern template, optional). The template uses it to mark that a stop is flexible.

Collection Points

Purpose

The Swiss profile distinguishes two types of stop place (Resource Frame):

Table: Types of stop place

TypeOfPlace Name (de / en) Meaning
regularStop Reguläre Haltestelle / Regular Stop Regular stop from classic public transport.
drtCollectionPoint Sammelpunkt / Collection Point Irregular stop used in demand responsive transport.

Both are defined as TypeOfPlace in the ValueSet ch:1:ValueSet:TypesOfPlace of the ResourceFrame. The ValueSet is expected and must have these two entries (TypesOfPlace template, ResourceFrame template).

The type is independent of StopPlaceType: StopPlaceType describes the kind of stop place (e.g. onstreetBus, values in the sheet StopPlaceType of the mapping table), the TypeOfPlace says whether it is a regular stop or a collection point.

Example

In NeTEx, a StopPlace refers to its TypeOfPlace with placeTypes/TypeOfPlaceRef (directly after Centroid):

<StopPlace id="ch:1:sloid:7000" version="1">
  <!-- ... -->
  <Name>Bern</Name>
  <Centroid>
    <!-- ... -->
  </Centroid>
  <placeTypes>
    <TypeOfPlaceRef ref="regularStop" version="1"/>
  </placeTypes>
  <!-- ... -->
  <StopPlaceType>railStation</StopPlaceType>
  <!-- ... -->
</StopPlace>

Purpose

The types 3 to 5 have a service area (Bediengebiet). Type 3 (corridor) is modelled as an area as well. The modelling follows the Swiss area example in the NeTEx repository (examples/functions/drt/CH_DRT_Area_mybuxi.xml), split between the two file types like the regular stops:

Table: Elements for service areas

Element Frame File type Purpose
FlexibleStopPlace with one FlexibleArea SiteFrame/flexibleStopPlaces SITE_OFFER The area with its geometry.

FlexibleStopAssignment ServiceFrame/stopAssignments NETWORK_OFFER Links the ScheduledStopPoint to the FlexibleStopPlace and FlexibleArea, like PassengerStopAssignment for regular stops.

Usage Notes

  • The geometry of the FlexibleArea is mandatory: either gml:Polygon or gml:MultiSurface (choice in the XSD), in EPSG:4326. The schematron does not check this, because the template annotations cannot express the choice and do not handle the gml namespace; the template marks it as expected.
  • members is optional. It lists the collection points (TypeOfPlace drtCollectionPoint, see Collection Points) of the area, if the service has any. A service without fixed stops (type 5) has no members, only the geometry.
  • members and the references in the FlexibleStopAssignment point into the other file type. They use versionRef instead of version: with version, the XSD key reference requires the referenced object in the same document.
  • HailAndRideArea is not used.
